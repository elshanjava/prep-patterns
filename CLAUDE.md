# Контекст проекта

Личный репозиторий подготовки к лайв-кодингу (Java / финтех, Revolut-подобный формат).
Читается автоматически в начале каждой сессии — сюда кладём то, что должно пережить
конец чата и переезд на другую машину.

**Цель сейчас:** живое кодирование и обсуждение решений. Алгоритмы (LeetCode) сознательно
вне рамок — их добавим отдельно.

## Конвенции тестов (выведены болью, нарушать дорого)

**`countDown()` освобождающей защёлки — только в `finally`.**
Если ассёрт упал раньше, ждущие потоки остаются припаркованными, а `pool.close()`
внутри вызывает `awaitTermination(1, DAYS)`. Сборка не падает — она **висит сутки**.
Ровно та же логика, что `permits.release()` в `finally` внутри `Bulkhead`.

**На каждом `await()` в тесте — таймаут.**
`latch.await()` без срока превращает любую поломку в зависание. Правильно:
`assertThat(latch.await(5, TimeUnit.SECONDS)).isTrue();` — красный тест за 5 секунд
с внятным сообщением.

**`countDown()` вызывает тот поток, чьё состояние проверяем, и в нужной точке.**
Сигнал «я захватил ресурс» должен подавать сам воркер уже **внутри** критической секции.
Вызов из основного потока до `submit()` обнуляет счётчик раньше времени, и `await()`
проскакивает впустую.

**Блокировку проверять через `Thread.State`, а не через `isAlive()`.**
`isAlive()` истинно и для потока, крутящего busy-wait на 100% ядра. Замер:
`take()` → `WAITING`, CPU 0 мс; `while (poll() == null) {}` → `RUNNABLE`, CPU 204 мс
за 200 мс ожидания. Обе защёлки при этом ведут себя одинаково.

**Каждый новый тест проверять мутацией.**
Сломать боевой код в одну строку и убедиться, что тест краснеет. Зелёный после мутации
тест ничего не проверяет. Так были найдены: незакрытая ветка `HALF_OPEN` в брейкере,
утечка разрешений без `release()` в `finally`, busy-wait в очереди.

**Пул обязан вмещать все задачи, которые ждут друг друга.**
Задача, припаркованная на защёлке, держит свой поток. Пул меньше нужного →
thread starvation deadlock, тест висит вместо падения.

**Демка, печатающая утверждение, ≠ проверка.**
Повторяющаяся находка: `System.out.println("backpressure сработал")` при коде, который
backpressure не делает. Проверять поведение, а не текст вывода.

**Лог из нескольких потоков показывает порядок печати, а не порядок событий.**
Поэтому ассёрты — по счётчикам (`AtomicInteger`), а не по последовательности строк.

## Метод TDD, которым тренируемся

Разбивка задачи — работа кандидата, не интервьюера. Универсальный порядок:

```
1. API           сигнатуры, типы, что бросает
2. Happy path    простейший осмысленный сценарий
3. Вариации      несколько элементов, порядок, повторы
4. Границы       пусто, полно, capacity=1, некорректный аргумент
5. Ошибки        исключения, отмена, прерывание
6. Конкурентность   ВСЕГДА последней
```

Цикл: **RED (увидеть падение своими глазами) → GREEN (минимальный код) → REFACTOR (только на зелёном)**.
Каждый шаг добавляет ровно одну новую способность. Тест, зелёный с рождения, —
либо страховка (проверить мутацией), либо признак того, что на прошлом шаге написано лишнее.

Первые 3 минуты собеседования: проговорить понимание задачи, предложить порядок шагов,
задать 3-4 вопроса (можно ли `java.util.concurrent`; нужны ли timed-варианты; `null`
разрешён; нужна ли fairness). Это создаёт контракт на случай нехватки времени.

## Тренировка собеседования: где остановились

Формат: **мок-интервью** — Claude ставит задачу в две-три строки и ведёт её как
интервьюер, пользователь отвечает как кандидат; паузы на разбор по ходу.
Отрабатываются и первые три минуты (понимание + план + вопросы), и живой
red-green-refactor в коде.

### Прогон 2026-09-04/07: bounded blocking queue — ЗАВЕРШЁН

`zpractice/blockingqueue/BoundedBlockingQueue2` доведён до 8 зелёных тестов:
put/take, FIFO, кольцо, `capacity<=0`, `put(null)`, блокировка `put` на полной,
блокировка `take` на пустой, нагрузочный 4x4 по 250 элементов.

Реализация: `ReentrantLock` (non-fair) + `notFull`/`notEmpty`, `count`, `%`,
`size()` под локом. Проверено мутациями — каждая ловится своим тестом:

| Мутация | Ловит |
|---|---|
| убрать `if (capacity <= 0)` | `shouldThrowExceptionThenCapacityLessOne` |
| убрать `if (a == null)` | `shouldThrowExceptionThenInputNull` |
| убрать `notEmpty.await()` | `shouldBlockingTakeThenEmpty` |
| **`while` → `if` в обоих `await`** | **нагрузочный** (единственный, кто его видит) |

Не покрыто сознательно: прерывание (`interrupt` на `await`), timed `offer`/`poll`.

### Прогон 2026-09-07/08: load balancer — ЗАВЕРШЁН (основное)

Постановка: реестр бэкендов, `get()` отдаёт **один** адрес, много потоков,
потолок 10 серверов, стратегии RANDOM (дефолт) и ROUND_ROBIN.

**11 зелёных** в `test/tdd/loadbalancer/LoadBalancer2Test`: `register`+`get`, `size`,
рандом (100 вызовов, `Set`), round-robin с заворотом, `deregister` уменьшает size,
`deregister` неизвестного → IAE, `get()` на пустом → ISE, дубликат → IAE,
`register(null)` → NPE, лимит 10 → ISE, **конкурентный get+deregister**.

Реализация `zpractice/loadbalancer/LoadBalancer2`: `ArrayList` + `AtomicInteger index`
+ `Strategy` в конструкторе, `Math.floorMod`, **`ReentrantReadWriteLock`** —
write на register/deregister, read на get/size. Здесь RWLock уместен (в отличие от
очереди, где `take` мутирует): `get()` — настоящее чтение списка.

Два урока прогона, стоят того чтобы помнить:
- **Флакающий красный.** Первая версия конкурентного теста: 10 серверов, потом
  одноразовые deregister — красный ловился 1 раз из 3 (окно гонки узкое). Лечится
  **непрерывным churn** (потоки в цикле снимают И возвращают сервер) — окно открыто
  весь тест, красный стабильный. Урок: concurrency-тест обязан краснеть надёжно.
- **Deadlock от неверного `finally`.** В `deregister` было `finally { writeLock().lock() }`
  вместо `unlock()` → лок не отпущен → все геттеры навсегда встали на `readLock`,
  `done.await()` не досчитался → тест **завис** (не упал). `finally` есть, но действие
  в нём неверное. Хорошая иллюстрация правила «освобождающее действие в finally».

**Сознательно НЕ покрыто** (кандидат решил закрыть кату): register-гонка под нагрузкой
(10 уникальных + 10 дублей → size==10, отдельный тест — эталон её проверяет);
«снятый сервер больше не выдаётся» (поведенческий, не через size); round-robin после
deregister; **мутация конкурентного теста** (убрать лок → убедиться, что с churn красный
теперь стабильный, а не 1/3) — единственный незакрытый пункт строгости.

### Прогон 2026-09-09: rate limiter — ЗАВЕРШЁН

Постановка: `boolean allow(String userId)`, N запросов за окно, разные юзеры независимо.
Выбрали **sliding window log** (точный, детерминированный под инжектом времени) +
**инъекция времени** (`LongSupplier` в конструкторе; в тесте `AtomicLong now`, `now::get`,
перематываем `now.set(...)` вместо `Thread.sleep`) — это звезда каты, аналог `Clock` в TTL-кэше.

**6 однопоточных зелёных** в `test/tdd/ratelimiter/RateLimiter2Test`: под лимитом → true;
над лимитом (N true, N+1 false); **окно истекло → снова true** (перемотка времени);
per-user изоляция; конструктор `maxRequests<=0`→IAE; `windowMs<=0`→IAE.

Реализация `zpractice/ratelimiter/RateLimiter2`: `HashMap<String, Deque<Long>>`,
`computeIfAbsent` даёт деку юзера; в `allow` — снимок `now = time.getAsLong()`,
`while`-eviction протухших (`now - peekFirst() >= windowMs`, removeFirst), затем
`size() < maxRequests` → `addLast(now)`.

**7-й тест — конкурентность:** `allowed_threadSafe_exactlyLimitPass` (limiter(10,10000),
`ready`/`done`, ассёрт `allowed == 10`). Green: `HashMap`→`ConcurrentHashMap` +
`synchronized (timestamps)` на деке юзера (per-user лок, как в эталоне и idempotency).
**Незакрытый пункт строгости (как и в load balancer):** тест НЕ доказан мутацией — с
50 потоками он был зелёным даже на несинхронизированном коде (гонка check-then-act не
триггерилась); подняли до 1000 потоков и добавили синхронизацию, но что именно даёт
зелёный — сильный тест или уже правильный код — мутацией не проверяли. Кандидат решил
закрыть кату. Эталон — `src/tdd/ratelimiter/RateLimiter.java`.

Мелкие хвосты: лямбда-параметр-ключ назван `times` (→ `k`); «maxRequest» без `s`;
1000 платформенных потоков в тесте — тяжело (лучше виртуальные / меньше×цикл).

### Прогон 2026-09-09: transfer (перевод денег) — ЗАВЕРШЁН

Постановка: `transfer(from, to, amount)`, атомарность, недостаточно средств, много потоков.
Новый концепт (не было в прошлых катах): **порядок захвата ДВУХ локов против deadlock**.
Деньги — `long` в центах (не `double`: 0.1+0.2 непредставимо, ошибки копятся).

**6 зелёных** в `test/tdd/transfer/TransferService2Test`: базовый перевод (debit+credit);
недостаточно средств → `InsufficientBalanceException` + балансы не тронуты; тот же счёт → IAE;
сумма<=0 → IAE; **атомарность под нагрузкой** (нет overdraft); **★ дедлок** (A→B и B→A
одновременно → не виснет).

Реализация `zpractice/transfer/{Account2,TransferService2,InsufficientBalanceException}`:
`Account2` с package-private `debit`/`credit` (менять баланс только через сервис);
`transfer` — валидация → **лок обоих счетов в порядке по `id`** (`compareTo`, консистентно
независимо от направления) → проверка баланса под локом → debit/credit.

**Ключевой инсайт (кандидат разложил сам):** что ЛОЧИТЬ — по id (единый тотальный порядок,
ломает circular wait); что СПИСЫВАТЬ — по направлению. Разделение этих двух — суть.

**★ Дедлок-тест ДОКАЗАН естественной мутацией** (в отличие от rate limiter): был RED на
наивных локах `synchronized(from){synchronized(to)}` (зависание → `done.await(100ms)`→false),
стал GREEN на упорядоченных по id. Своими глазами видели переход — тест реально стережёт.
Таймаут на `done.await` кандидат поставил сам (без него дедлок вешает сборку).

**Мелочи не закрыл:** избыточная предпроверка баланса до лока (просил убрать 2×, оставил —
незалоченное чтение + дубль внутрилоковой проверки); 2000 потоков в атомарном тесте (тяжело);
атомарный тест (overdraft) слабоват — green даже на баге, как и в rate limiter.

### Прогон 2026-09-11: LRU cache — теория + эталон (итог см. в прогоне 2026-09-14/15)

Решили делать **с нуля** (HashMap + двусвязный список), не через LinkedHashMap.
Теория разобрана плотно: почему `HashMap<K,Node>` + DLL даёт O(1); **почему не дека**
(LRU двигает элемент из СЕРЕДИНЫ на каждом обращении → дека O(1) только на концах, нужен
DLL с прямым указателем на узел из мапы); почему **двусвязный** (нужен предшественник для
O(1)-удаления); зачем Node хранит key (вытеснение → `map.remove(tail.prev.key)`);
**get МУТИРУЕТ** (переставляет узел) → `synchronized`, не RWLock (контраст с load balancer);
внутренности `LinkedHashMap` (Entry = Node + before/after, поэтому он даже ЭКОНОМНЕЕ ручного
`HashMap<K,Node>+DLL`, где ключ хранится дважды).

**Кандидат застрял на ручной реализации** (честно сказал «сложно, не перегибаем?»):
- перепутал **generic-параметр и класс** — написал `class LruCache2<K, Node>` (Node как
  переменная типа), потерял `V`; надо `<K,V>` + **вложенный класс** `Node`;
- в `put` **не связал узел со списком** (создал Node, положил в мапу, но `addFirst` не звал);
  вытеснял не тот узел (`n.next.key` у нового узла → NPE вместо `tail.prev`);
- манипуляция указателями DLL далась тяжело — попросил дать эталон для изучения.

**По просьбе кандидата написан ЭТАЛОН** (не его тренировка): `src/tdd/lrucache/LruCacheFromScratch.java`
(HashMap + DLL + sentinel head/tail, `addFirst`/`remove`/`moveToFront`, `get` освежает,
`put` обновляет+освежает или вытесняет хвост, `synchronized`) + `LruCacheFromScratchTest`
(8 зелёных: happy, absent→null, вытеснение старейшего, **get освежает — LRU≠FIFO**,
put существующего обновляет без роста, capacity<=0→IAE, keysOldestFirst порядок,
конкурентность-инварианты). Решение: `LruCacheFromScratch` = ЭТАЛОН; старый `LruCache`
на `LinkedHashMap` оставлен «для истории и сравнения». Конкурентный тест мутацией ДОКАЗАН (замерено 2026-09-14:
снятие `synchronized` ловится 4 прогона из 4) — ранняя запись об обратном неверна.

**ЗАВЕРШЕНО кандидатом 2026-09-14:** `zpractice/lrucache/LruCache2` дописан **своими руками**
до 6 зелёных: get/put, вытеснение старейшего, **get освежает (LRU≠FIFO)**, put существующего
обновляет без дубликатов, `capacity<=0`→IAE, конкурентность. `HashMap<K,Node>` + двусвязный
список с sentinel'ами + `synchronized` (get мутирует → лок, не RWLock).

Продавил DLL сам через ошибки (лечили по ходу): порядок строк в `addFirst` (`head.next=node`
до `head.next.prev=node` → петля на себя); забыл `addFirst` в `put` (узел не в списке,
`tail.prev`=sentinel); **сирота-узел при повторном ключе** — старый `put` плодил дубликат
с тем же key, старый узел висел в списке и при вытеснении сносил ЖИВОЙ ключ из мапы
(лечится веткой «existing → обновить+moveToFront, не создавать»).

**Конкурентный тест ДОКАЗАН мутацией** (в отличие от rate limiter/LB): 3/3 RED без лока →
4/4 GREEN с `synchronized`. DLL хрупок — гонка корраптит указатели надёжно (NPE + HashMap
под структурной модификацией), поэтому красный стабильный. Сильный страж.

### Сессия 2026-09-13/14: устройство DLL разобрано по вопросам кандидата

Кандидат сам вёл разбор вопросами — модель сложилась. **Не объяснять заново**, вот что
уже закрыто (каждый пункт подтверждён прогоном, не словами):

- **где вообще проставляются `prev`/`next`**: только 8 присваиваний на весь класс —
  2 в конструкторе (`head.next = tail; tail.prev = head`), 4 в `addFirst`, 2 в `remove`.
  `get`/`put` ссылки не трогают вовсе, `moveToFront` = `remove` + `addFirst`.
- **порядок в `addFirst` критичен**: `head.next = n` стирает старое значение, поэтому
  читать `head.next` надо раньше (шаг 2). Иначе ссылка на бывшего первого потеряна.
- **стражи — не записи**: самый свежий это `head.next`, самый старый — `tail.prev`.
  Ошибка `tail.key` даёт `null`, `map.remove(null)` молча ничего не делает → мапа и
  список расходятся без исключения.
- **у стражей работает одно поле из четырёх**: `head.next` и `tail.prev`;
  `key`/`value` и `head.prev`/`tail.next` не читаются никогда (остаются null).
- **кольца нет** — список линейный, `head.prev == null`, `tail.next == null` навсегда.
- **«стражи ≈ out of bounds»** (его формулировка, верная): вне границ данных, внутри
  границ структуры. Аналог `end()` в C++ и полуинтервала `[begin, end)`;
  `n != tail` в цикле — это `it != end()`.
- **почему не сделать head/tail ссылками на реальные крайние узлы** (его предложение):
  замерено — такие ссылки за 6 операций меняются 6 раз и дважды становятся null →
  4 ветвления в `addFirst`/`remove`, `final` невозможен. Со стражами 0 ветвлений,
  оба поля `final`. Демо с одной забытой веткой (`else last = n.prev`): `oldest()`
  возвращает уже вытесненный узел, следующее вытеснение снимает труп — **тихая порча,
  без исключения**.
- **одного кольцевого стража достаточно** (его наблюдение, верное): `s.next = s.prev = s`,
  те же 6 присваиваний, 0 ветвлений, на 1 объект меньше. Два стража берут ради
  читаемости (имена концов, `n != tail` вместо `n != s`, отладка без вечного цикла).
  Для сравнения: `java.util.LinkedList` в JDK вообще без стражей — отсюда ветки в `unlink()`.
- **почему не отдельный класс для стражей**: тогда `prev`/`next` типизируются общим
  предком без `key`, и на вытеснении нужен каст `((Entry) tail.prev).key` — проверка на
  null меняется на проверку типа, `ClassCastException` вместо `NullPointerException`.
  Плюс `addFirst(head)` становится типально законным. Интрузивные списки (Linux `list_head`)
  так делают ради участия объекта в НЕСКОЛЬКИХ списках; в LRU узел в одном списке.
- **LRU против FIFO — одна строка**: FIFO вытесняет по порядку вставки, LRU по порядку
  обращений; различает `moveToFront` в `get` **и в `put` существующего ключа**.
  В JDK это третий аргумент `LinkedHashMap(cap, 0.75f, accessOrder)`: замерено,
  `false` → `[b, c, d]`, `true` → `[c, a, d]`.
  **Мораль для тестов:** без теста «обращение освежает» реализация FIFO проходит
  ВСЕ остальные проверки.

**Сделана визуализация** (ссылка в «Наглядных материалах»): обе структуры на одном экране,
каждое присваивание — отдельный шаг с подсветкой строки, сценарии «каноничный прогон»,
«LRU против FIFO», «обновление ключа», ручные put/get, переключатель освежения.

- `CopyOnWriteArrayList` — отписка ИЗНУТРИ обработчика на `ArrayList` даёт

- `listener.accept(event)` — вызов тела лямбды; `received::add` = `e -> received.add(e)`,

**Решения по дизайну (кандидат назвал сам):** доставка по иерархии — НЕТ, точное совпадение;

### Прогон 2026-09-16: URL shortener — теория (ката дописана, см. прогон ниже)

По просьбе кандидата (сказал «не знаю» на большинство вопросов) разобрана теория целиком.
Закрыто (не повторять с нуля):
- **API:** `shorten(url)→code` / `resolve(code)→url`.
- **base62** (звезда каты): счётчик `AtomicInteger` → код. 62 символа (`0-9 a-z A-Z`,
  все URL-safe); больше алфавит → короче код (`62^6 ≈ 56 млрд` в 6 символах). Механика =
  перевод в 62-ричную систему: `n % 62` → индекс символа, `n /= 62`, повторять, потом
  ПЕРЕВЕРНУТЬ (остатки дают цифры от младшей). Пример: `12345 → "3d7"`. Счётчик (не хеш)
  гарантирует уникальность → коллизий нет; минус — коды угадываемы (в проде random/hash).
- **Две мапы** `urlToCode` + `codeToUrl`: HashMap ищет O(1) ТОЛЬКО по ключу. `resolve` ищет
  по коду (нужен `codeToUrl`), дедуп в `shorten` ищет по URL (нужен `urlToCode`). Одной
  мапой — только одно направление быстрое; второе стало бы O(n) перебором. Кандидат долго
  не понимал «почему нельзя одну» — разжевали: мапа односторонняя, по значению не ищет.
- **Идемпотентность `shorten`**: тот же URL → тот же код через `computeIfAbsent` (атомарно).
- **Потокобезопасность**: `ConcurrentHashMap` (обе мапы) + `AtomicInteger` (иначе `int++`
  под гонкой даёт два URL один код); `computeIfAbsent` вместо `containsKey`+`put` (гонка →
  дубль кода).
- **Краевые**: `resolve` неизвестного → `NotFoundException` (не null); null/пустой URL —
  решить (отвергать); переполнение счётчика → `int` в минус → `encode` вернёт "" (лечить `long`).

Добавил прогон 2026-09-11 (LRU cache):
- **сильное:** глубокие концептуальные вопросы (почему Node, почему не дека, память
  LinkedHashMap) — реально хочет понять, а не скопировать; трезво оценил силы («не перегибаем?»)
  и попросил эталон вместо того, чтобы буксовать — нормальная стратегия обучения;
- **промах — generic vs класс:** написал `class LruCache2<K, Node>` (Node как параметр типа,
  а не определённый класс), потерял `V`. Путаница «объявить переменную типа» ≠ «определить класс»;
- **промах — DLL не связал:** в `put` создал узел и положил в мапу, но в список не вставил
  (`addFirst` забыл), вытеснял `n.next` (нового узла) вместо `tail.prev`;
- ручной двусвязный список — объективно трудная часть; ему тяжело даётся манипуляция
  указателями. На будущих DLL-задачах давать sentinel-шаблон `addFirst`/`remove` заранее;
- нейминг снова: `returnStoredValue`/`evictOldest` без `s`.

### Разобранное по ходу (не повторять с нуля)

- `IllegalArgumentException` vs `IllegalStateException`: аргумент негоден сам по себе
  против «объект не в том состоянии». Полно/пусто → ISE, дубликат/не найден → IAE.
- Тест на случайность: либо свойство (`Set` + `containsExactlyInAnyOrder`), либо
  внедрить `Random` с зерном. Флакучесть посчитана: 3 вызова из 3 серверов —
  ложный красный в 78% прогонов, 10 — 5%, 100 — практически ноль.
- `ThreadLocalRandom` — синглтон, состояние в полях `Thread`; хранить в поле не ломает
  (замерено), но `setSeed` бросает `UnsupportedOperationException`, засеять нельзя.
  Общий `new Random()` на 8 потоков: 2404 ms против 10 ms у `ThreadLocalRandom`.
- `ReentrantLock(true)` (fair) против дефолтного: 5024 ms против 33 ms на 4 потоках
  по 500k захватов — в 152 раза. Fairness берут осознанно, не «для надёжности».
- Переполнение round-robin: `getAndIncrement()` на `MAX_VALUE` уходит в минус,
  `-2147483648 % 3 = -2` → `get(-2)`. Лечится `Math.floorMod`. При 1000 RPS
  наступает через ~25 дней.
- `List.remove(Object)` vs `remove(int)` — на `List<Integer>` ловушка.
- Недостижимое состояние (время, случайность, счётчик у границы) — не создавать
  внутри, а принимать снаружи или выносить в чистую функцию.

В катах шло **проектирование**: API, структуры данных, red-green. В стримах проектировать
нечего — задача формулируется фразой, ответ это выражение в 3–5 строк. Проверяется
**беглость и распознавание идиомы** плюс знание ловушек. Цикл:
```
формулировка словами -> пишешь пайплайн вслепую -> прогон -> разбор идиомы
```
Red-green не нужен: тест пишется ДО и является частью условия.

## Как работать с пользователем

Русский язык. Объяснения — с разбором механики, а не «сделай так». Он проверяет
утверждения и замечает несоответствия, поэтому: измерять, а не предполагать; при ошибке
исправляться прямо и без лишних слов.

Ценит, когда вывод подкреплён прогоном — `jstack`, `jshell`, мутация, замер времени.
Слабые места, выявленные опросом: `shutdown` / `shutdownNow` / ядовитая пилюля;
`InterruptedException` как отмена и восстановление флага; разница «ждёт» против
«отказывает мгновенно» (fast-fail).
