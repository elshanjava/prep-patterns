# Контекст проекта

Личный репозиторий подготовки к лайв-кодингу (Java / финтех, Revolut-подобный формат).
Читается автоматически в начале каждой сессии — сюда кладём то, что должно пережить
конец чата и переезд на другую машину.

**Цель сейчас:** живое кодирование и обсуждение решений. Алгоритмы (LeetCode) сознательно
вне рамок — их добавим отдельно.

## Конвенции тестов (выведены болью, нарушать дорого)

**`countDown()` освобождающей защёлки — только в `finally`.**
Если ассёрт упал раньше, ждущие потоки остаются припаркованными, а `pool.close()`
внутри вызывает `awaitTermination(1, DAYS)`. Сборка не падает — она **висит сутки**.
Ровно та же логика, что `permits.release()` в `finally` внутри `Bulkhead`.

**На каждом `await()` в тесте — таймаут.**
`latch.await()` без срока превращает любую поломку в зависание. Правильно:
`assertThat(latch.await(5, TimeUnit.SECONDS)).isTrue();` — красный тест за 5 секунд
с внятным сообщением.

**`countDown()` вызывает тот поток, чьё состояние проверяем, и в нужной точке.**
Сигнал «я захватил ресурс» должен подавать сам воркер уже **внутри** критической секции.
Вызов из основного потока до `submit()` обнуляет счётчик раньше времени, и `await()`
проскакивает впустую.

**Блокировку проверять через `Thread.State`, а не через `isAlive()`.**
`isAlive()` истинно и для потока, крутящего busy-wait на 100% ядра. Замер:
`take()` → `WAITING`, CPU 0 мс; `while (poll() == null) {}` → `RUNNABLE`, CPU 204 мс
за 200 мс ожидания. Обе защёлки при этом ведут себя одинаково.

**Каждый новый тест проверять мутацией.**
Сломать боевой код в одну строку и убедиться, что тест краснеет. Зелёный после мутации
тест ничего не проверяет. Так были найдены: незакрытая ветка `HALF_OPEN` в брейкере,
утечка разрешений без `release()` в `finally`, busy-wait в очереди.

**Пул обязан вмещать все задачи, которые ждут друг друга.**
Задача, припаркованная на защёлке, держит свой поток. Пул меньше нужного →
thread starvation deadlock, тест висит вместо падения.

**Демка, печатающая утверждение, ≠ проверка.**
Повторяющаяся находка: `System.out.println("backpressure сработал")` при коде, который
backpressure не делает. Проверять поведение, а не текст вывода.

**Лог из нескольких потоков показывает порядок печати, а не порядок событий.**
Поэтому ассёрты — по счётчикам (`AtomicInteger`), а не по последовательности строк.

## Метод TDD, которым тренируемся

Разбивка задачи — работа кандидата, не интервьюера. Универсальный порядок:

```
1. API           сигнатуры, типы, что бросает
2. Happy path    простейший осмысленный сценарий
3. Вариации      несколько элементов, порядок, повторы
4. Границы       пусто, полно, capacity=1, некорректный аргумент
5. Ошибки        исключения, отмена, прерывание
6. Конкурентность   ВСЕГДА последней
```

Цикл: **RED (увидеть падение своими глазами) → GREEN (минимальный код) → REFACTOR (только на зелёном)**.
Каждый шаг добавляет ровно одну новую способность. Тест, зелёный с рождения, —
либо страховка (проверить мутацией), либо признак того, что на прошлом шаге написано лишнее.

Первые 3 минуты собеседования: проговорить понимание задачи, предложить порядок шагов,
задать 3-4 вопроса (можно ли `java.util.concurrent`; нужны ли timed-варианты; `null`
разрешён; нужна ли fairness). Это создаёт контракт на случай нехватки времени.

## Тренировка собеседования: где остановились

Отрабатываем **первые три минуты** живого кодирования: формулировка задачи от
интервьюера в две-три строки, кандидат отвечает пониманием + планом + вопросами.

**Прогон от 2026-09-04 — bounded blocking queue, формат «мок-интервью с паузами
на разбор» (Claude = интервьюер, пользователь = кандидат).** Открытие вышло заметно
сильнее прошлого раза:

| Критерий | Прошлый раз | 2026-09-04 |
|---|---|---|
| `throws InterruptedException` | после подсказки | сам |
| FIFO | сам | сам |
| Критический вопрос «с нуля / concurrent» | не задал | задал первым |
| Вопросы интервьюеру | ноль до двойного пинка | вёл диалог |
| Самокоррекция дизайна (RWLock → ReentrantLock + 2 Condition) | — | сам развернул |
| Fairness (barging/starvation vs throughput, дефолт non-fair) | — | обосновал после пробы |

Остаточные слабые места: «нужно ли ещё что-то реализовать?» — всё ещё пассивная
формулировка, перекладывает проектирование (правильно: **предлагать**, а не спрашивать
разрешения); блокировку в плане по-прежнему не называет **явным шагом**, растворяет
в «многопоточности».

**Вопросы, которые надо задавать (в порядке важности):**
можно ли `java.util.concurrent` или нужна реализация с нуля (критический — меняет
задачу с одной строки на сорок минут); нужны ли timed `offer`/`poll`; разрешён ли `null`;
нужна ли справедливость (fairness).

**Эталонный план для этой каты:**
```
1. put/take одного элемента
2. FIFO на нескольких
3. кольцевой буфер: заворачивание индексов
4. capacity <= 0 -> IllegalArgumentException
5. take на пустой БЛОКИРУЕТСЯ, просыпается после put
6. put на полной БЛОКИРУЕТСЯ, просыпается после take
7. прерывание во время ожидания -> InterruptedException
8. нагрузочный: N продюсеров, M консьюмеров, ничего не потеряно
   (он же ловит `if` вместо `while` в await)
```

**Где остановились в прогоне 2026-09-04 (продолжить с этой точки):**
Пишем `zpractice/blockingqueue/BoundedBlockingQueue2` по red-green-refactor вживую.
Пройдено:
- шаг 1 (`putThenTakeElement`) — GREEN. Кандидат впервые взял минимум (одно поле `item`),
  не потащил весь буфер вперёд. Красный сначала имитировал стабом (`return null`),
  потом усвоил, что честнее «естественный красный по поведению».
- шаг 2 (`putAndReturnInFifoOrder`) — GREEN. Ввёл `Object[] items` + `head` + `tail`.
  `%` и `count` **сознательно отложены** (ни один тест не требует) — это правильно.
  Refactor-чекпоинт проговорил вслух («чисто, не трогаю») — то, что раньше пропускал.

Текущее состояние кода (`BoundedBlockingQueue2`): поля `items/head/tail`, конструктор
`(int capacity)` создаёт массив; `put` = `items[tail]=a; tail=tail+1` (БЕЗ `%`);
`take` = читает `items[head]`, зануляет ячейку, `head=head+1` (БЕЗ `%`); ни `count`,
ни лока, ни `Condition` ещё нет. Тест-класс: два зелёных теста, `setUp` даёт capacity 5.

**Следующий шаг (ему заданы 3 наводящих вопроса, ждём ответ):** тест на **оборот кольца**,
который заставит ввести `%`. Вопросы кандидату: какую ёмкость взять (маленькую); какая
последовательность put/take загонит `tail` за конец (нужны take между put, иначе упрёшься
в «полно»); какой будет красный (сейчас без `%` — `ArrayIndexOutOfBoundsException`, а не
несовпадение значений). Дальше по эталонному плану: capacity<=0, take блокируется,
put блокируется, прерывание, нагрузка.

**Прочие варианты продолжения:** незнакомая задача «кэш с TTL» (неочевидное решение —
инъекция `Clock`, иначе тест на истечение упирается в `Thread.sleep`).

## Правки в коммитнутом коде за сессию 2026-09-04 (закоммичены в 93621bc)

- `concurrent/retry/good/RetryPolicy` — `RandomGenerator.getDefault()` заменён на
  `ThreadLocalRandom.current().nextLong(jitterMs)`. Причина: `getDefault()` ищет
  «L32X64MixRandom» через ServiceLoader и падает `IllegalArgumentException` в конструкторе
  на кривом Corretto-инсталле IntelliJ (Temurin в WSL — проходил, отсюда расхождение).
  `ThreadLocalRandom` всегда в `java.base`, без lookup. Чинило 14 падавших retry-тестов.
- `CircuitBreaker2Test.inHalfOpen_onlyOneProbeIsAllowed_othersFailFast` — три финальных
  ассёрта вынесены **за** `try (ExecutorService pool …)`. Внутри блока `cb.state()`
  читался сразу после `releaseProbe.countDown()`, обгоняя пробу (CAS HALF_OPEN→CLOSED
  ещё не случился) → флаки `was HALF_OPEN`. `pool.close()` за скобкой дожидается пробы.
  Рабочий сосед `CircuitBreakerTest` так и делал — потому и не флакал.
- `.idea/gradle.xml` — gradleJvm снова уводился на `#JAVA_INTERNAL` (JBR), IntelliJ
  переставлял на `corretto-21` (AppLocker error 1260). Переключить Gradle JVM на
  JBR/Temurin в UI, иначе слетает.

## Открытые хвосты

- Нет теста на **прерывание** (`interrupt` потока, стоящего на `await`) ни в одной
  из реализаций очереди. В `BoundedBlockingQueueTest` `interrupt()` встречается только
  как восстановление флага в `catch`, а не как проверяемое поведение.
- `BoundedBlockingQueue2Test` тащит неиспользуемые импорты (`CountDownLatch`,
  `AtomicInteger`, `AtomicReference`, `assertThatThrownBy`) — остались от прошлой
  версии класса, снесённой при перезапуске каты.
- Нет тестов у `LockingIdempotentProcessor`; спецификацию стоило бы гонять по обеим
  реализациям через `@ParameterizedTest` или общий базовый класс.
- Пакеты `completablefuture`, `readwritelock`, `threadpool` без тестов.
- `src/pattern/coding/MOCK_CASES.md` не упоминает LRU, bulkhead, blocking queue.

## Как работать с пользователем

Русский язык. Объяснения — с разбором механики, а не «сделай так». Он проверяет
утверждения и замечает несоответствия, поэтому: измерять, а не предполагать; при ошибке
исправляться прямо и без лишних слов.

Ценит, когда вывод подкреплён прогоном — `jstack`, `jshell`, мутация, замер времени.
Слабые места, выявленные опросом: `shutdown` / `shutdownNow` / ядовитая пилюля;
`InterruptedException` как отмена и восстановление флага; разница «ждёт» против
«отказывает мгновенно» (fast-fail).
